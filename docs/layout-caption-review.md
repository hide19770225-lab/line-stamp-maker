# 自動レイアウト・表情別セリフ提案・一括承認

## 無料方式の調査と採用方針

既存コードにはCanvasによる日本語文字描画、改行、実際のアルファ画素を用いた重なり判定、文字用のキャラクター縮小があります。これを拡張する方式は、新規依存・モデル配信・APIキーなしでGitHub PagesとiPhone向け画面に組み込めます。

| 方式 | 利点 | 本件の制約・採否 |
| --- | --- | --- |
| Canvas＋既存のアルファマスク | 無料・ブラウザ内。色の推測で消さず、形状全体をレイアウトできる | 採用。20px余白、文字サイズ・改行・位置とキャラクターの縮小を調整 |
| FaceDetector等のブラウザAPI | 実装されているブラウザでは顔の位置を検出可能 | 表情ラベルを直接保証しない。ブラウザ対応差があり、イラストの分類器として採用しない |
| MediaPipe Face Landmarker | 顔ランドマーク・ブレンドシェイプを端末側で推論可能 | モデル等の配布と端末検証が必要。ブレンドシェイプはこのキャラクターの感情分類の正解を保証しない |
| face-api.jsの表情モデル | 学習済みモデルによる人の表情推論が可能 | 緑のマスコット等で精度を保証できない。モデルを今回の実画像で評価したものではないため採用しない |
| 手動の表情選択＋日本語辞書 | 追加料金・キー・通信不要。分類できない画像を断定しない | 今回採用。各画像の表情を利用者が選び、短い候補を端末内で提案 |

参考資料：
- [MediaPipe Face Landmarker](https://ai.google.dev/edge/mediapipe/solutions/vision/face_landmarker)
- [face-api.js](https://github.com/justadudewhohacks/face-api.js)

これは方式・適用対象の比較であり、新しい学習モデルを本リポジトリの画像で評価した実験ではありません。自動の画像感情分類は実装していません。将来導入する場合は、人と異なるキャラクターの検証データ、モデルの利用条件、Safariの性能・メモリ・配布方法を別途検証する必要があります。

## 操作

1. 従来どおり画像を加工します。40個設定でも10個だけで試せます。
2. 結果一覧の **表情を選んでセリフ提案・20px自動レイアウト** を開きます。01〜40のうち加工済みの画像だけが表示されます。
3. 各画像の表情を手動選択します。笑顔・泣き顔・怒り・驚き・眠い・あいさつ・応援に対応。未分類は勝手に分類しません。手入力と次の候補にも対応します。「まとめて提案」は選択済みの表情だけを対象とします。
4. 一覧で内容と重複警告を確認します。この時点では元のセリフと完成画像は変更しません。
5. **20px余白・文字の自動配置** の指定を確認し、目視チェック後に **全セリフを承認し、変更した画像だけ生成** を押します。空のセリフは承認を止めます。セリフなしのスタンプは既存の通常制作から制作できます。
6. 個別編集画面から配置・フォント・サイズ・文字位置、20px設定を再調整できます。元画像、輪郭、白い部分、装飾の色データは変更しません。
7. セリフ承認とは別に、既存の透過目視確認を行ってから申請用ZIPを保存します。40個の申請用ZIPでは全40個とメイン・タブを必要とするチェックを維持します。

同じセリフは警告し、未使用の候補を優先します。候補を使い切った場合の重複も警告します。意図的に同じセリフを使う場合は、警告を確認して承認できます。

## 互換性と画像処理

- 新しい承認フローは20px安全配置を初期選択します。旧JSON・従来の制作フローは従来の10px配置を維持し、勝手に見た目を変えません。
- `style.safeMargin`（10または20）を既存のversion 1 JSONに省略可能な項目として保存します。旧JSONの値を補完して変更しません。承認後のセリフと安全配置は保存・復元できます。未承認の提案と表情選択は現在の画面内だけに保持し、JSONには保存しません。入力イベントが発生しない値の復元も承認時に読み直し、重複警告の再確認を求めます。
- 20pxモードではキャラクター配置・文字の実画素・影・角度を含めて領域を確保し、文字がキャンバス内に入ってもキャラクターの場所がない場合は文字サイズをさらに調整します。字形・色を描き換えず、必要な場合だけ縦横比を維持して縮小します。
- 長すぎる改行入力など、最小文字サイズでも入らない場合は既存のはみ出し・重なりエラーで確認を要求します。元の分割で切り落とされた部分を復元する機能ではありません。
- セリフと安全配置に差分がある画像だけを描画し直します。変更がないスタンプの画素・目視確認状態を維持し、関係するメイン・タブだけ更新します。検査情報の再利用はこの承認操作内だけで行い、他の編集では破棄します。生成失敗時は未生成の状態を保持し、PNG・ZIP保存や一括承認で古い画像を合格扱いにせず、再承認による生成を要求します。
- 画像差し替え・番号再割当・再分割後は、以前の画像を参照する下書きを引き継ぎません。個別セリフを変更した場合も古い提案で上書きしないよう下書きを同期します。
- 外部API・画像アップロード・学習モデル・フォントCDN・月額料金は追加していません。既存の消しゴム・透過・残留線除去・JSON・メイン240×240px・タブ96×74px・ZIP形式を維持します。

## 検証

- Node.js：52件成功（既存49件＋辞書・重複・JSONの3件）。
- 新規ブラウザ2スイート成功：10個と40個の提案・承認・重複警告・日本語改行・20px透明余白・文字重なり0・原本RGB/マスク不変・JSON保存・タッチ消しゴムとUndo・ZIPを検証。
- 1個だけセリフ変更した際、他の画像・メイン・タブを描画し直さず、40個のうち39個の目視確認状態が維持されることを検証。
- 6プリセット×3角度（−30/0/30度）の長い日本語で20px余白、重なり0、文字切れなし、白い本体・元RGB・マスクの不変を検証。
- 既存12ブラウザスイートも成功。通常制作、自由分割、全申請枚数、JSON、文字デザイン、一括確認、前回の10個セリフ反映、失敗状態の管理、透過・消しゴム・Undo/Redo、実09/10の残留線除去とZIPを回帰確認。
- 入力イベントなしで復元された提案は実際の入力値から読み直して再確認を要求。画像生成を意図的に失敗させても未生成状態が残り、古い画像のZIP保存を禁止し、再承認で復旧できることを検証。
- JSON再読込・再加工後も20px配置・セリフ・画素ハッシュが完全一致。
- 出力ZIPをPythonで独立デコードし、10個・40個の全PNGとプレビューのRGBA一致、20px透明余白、メイン・タブの寸法、容量、PNG/ZIP CRCを検査。

実機iPhone Safari・ホーム画面追加版は未確認です。ブラウザ検証はChromiumのiPhone 13タッチ設定です。手動の表情選択に画像分類の精度保証という概念はなく、利用者が表情に合う候補を選びます。
